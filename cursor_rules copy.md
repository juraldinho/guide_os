# Guide OS - Cursor Rules

## Главная цель проекта

Довести Guide OS до рабочего MVP максимально быстро, просто и безопасно.

Приоритеты:

1. Рабочий MVP
2. Простая архитектура
3. Надёжный код
4. Минимум лишних изменений
5. Быстрый запуск

Главный принцип:

Запущенный MVP > идеальная система


---

# ОБЩИЕ ПРАВИЛА

Перед любыми изменениями всегда выполняй следующий порядок:

ANALYZE → PLAN → CODE

Никогда не переходи сразу к написанию кода.


---

# ОБЯЗАТЕЛЬНЫЙ АЛГОРИТМ РАБОТЫ

Перед каждой задачей:

1. Проанализируй существующий код.

2. Покажи какие файлы будут изменены.

3. Объясни зачем нужен каждый файл.

4. Опиши риски.

5. Только после этого предлагай код.

Если задача не требует изменений файла — не меняй его.


---

# ЧТО ЗАПРЕЩЕНО

Никогда самостоятельно НЕ:

- делать рефакторинг
- менять архитектуру
- переименовывать файлы
- переносить код между папками
- менять структуру проекта
- добавлять новые зависимости
- удалять существующий код
- переписывать рабочую логику
- оптимизировать код без запроса
- исправлять "на всякий случай"
- менять несколько функций одновременно
- добавлять функционал вне задачи


---

# ПРАВИЛО МИНИМАЛЬНЫХ ИЗМЕНЕНИЙ

Изменяй только минимально необходимое количество файлов.

Если задачу можно решить:

1 файлом → меняй 1 файл

2 файлами → меняй 2 файла

Не трогай остальной проект.


---

# ПРАВИЛО СТАБИЛЬНОГО КОДА

Если код работает — не переписывай его.

Даже если его можно написать красивее.

Рабочий код лучше красивого кода.


---

# АРХИТЕКТУРА ПРОЕКТА

Строго соблюдать разделение ответственности.

handlers/
Только UX и orchestration.

Разрешено:

- принимать сообщения
- вызывать сервисы
- показывать ответы

Запрещено:

- SQL запросы
- бизнес логика
- сложные вычисления
- длинные if/else конструкции


services/
Вся бизнес логика.

Тут находится:

- работа с турами
- расчёты
- конфликты дат
- календарь
- статистика
- доходы


database/
Только работа с БД.

Тут находится:

- подключение SQLite
- SQL запросы
- чтение данных
- запись данных


utils/
Только вспомогательные функции.

Например:

- форматирование
- валидация
- логирование


states/
Только FSM состояния.


keyboards/
Только Telegram кнопки.


---

# MVP ГРАНИЦЫ

Разрешён только функционал MVP.

Входит:

- Calendar
- Add Tour
- Income
- Stats
- Delete Tour
- Day Off

Не входит:

- AI функции
- Marketplace
- CRM
- роли пользователей
- совместные календари
- Google Calendar
- multi-language
- multi-currency
- аналитика будущих версий
- сложные интеграции


Если появляется идея вне MVP:

Не реализовывай её.

Пометь как:

POST-MVP IDEA


---

# БИЗНЕС ПРАВИЛА GUIDE OS

income = daily_rate

total_income = daily_rate × days_count

payment_status:

- paid
- unpaid

tour status:

- reserved
- confirmed

reserved:

- блокирует даты

confirmed:

- блокирует даты

пересечение туров:

- показывать предупреждение
- не запрещать сохранение

day_off:

- не является туром
- не считается доходом
- не считается рабочим днём
- только блокирует даты

cancelled:

- не используется в MVP

если тур отменён:

- удалить тур


---

# ПРАВИЛО БЕЗОПАСНОГО ИЗМЕНЕНИЯ

Перед написанием кода всегда отвечай:

FILES TO CHANGE

- file_1.py
- file_2.py

WHY

Причина изменений.

RISKS

Что может сломаться.

PLAN

Пошаговый план.

Только после этого показывай код.


---

# ПРАВИЛО НЕИЗВЕСТНОГО КОДА

Никогда не придумывай код.

Если файл не открыт:

Не делай предположений.

Скажи:

"I need to inspect this file first."

Если информации недостаточно:

Остановись и запроси анализ.


---

# ПРАВИЛО РАЗМЕРА ИЗМЕНЕНИЙ

Большие изменения запрещены.

Если изменение затрагивает больше 5 файлов:

Остановись.

Разбей задачу на маленькие подзадачи.


---

# КРАСНЫЕ ФЛАГИ

Если происходит одно из этих действий — остановись:

- handler > 150 строк
- SQL внутри handler
- бизнес логика внутри handler
- один запрос меняет больше 5 файлов
- появляется новая архитектура
- появляется новая зависимость
- начинается большой рефакторинг
- переписывается рабочий код


---

# ФОРМАТ ОТВЕТА CURSOR

Всегда отвечай так:

ANALYSIS

Что найдено.

FILES TO CHANGE

Какие файлы будут изменены.

RISKS

Что может сломаться.

PLAN

Что будет сделано.

WAITING FOR APPROVAL

Жди подтверждения.

После подтверждения:

CODE

Только необходимые изменения.


---

Не строй систему будущего.

Не строй платформу.

Строй только то, что нужно, чтобы сегодня работал MVP Guide OS.
